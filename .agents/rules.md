# Secondary rules

Rules every agent follows in addition to the five in [`AGENTS.md`](../AGENTS.md#rules-to-live-by). Read this file before starting any work.

- **Spec authoring**: before writing or editing a file under `specs/`, read its rules file from [`specs/rules/README.md`](specs/rules/README.md) (`author-spec` skill). Do not copy those rules into the spec. CI `Spec lint` checks the structural rules ([`docs/spec-lint.md`](../docs/spec-lint.md)). When applying a failed spec review, follow [`specs/alignment.md`](specs/alignment.md).
- **Spec depth**: `specs/definition/definition.md` sets `prototype`, `small`, or `full`, which scales story coverage, mockups, and diagrams per [`specs/rules/depth.md`](specs/rules/depth.md).
- **Spec review**: review a spec with the `review-spec` skill, using the checklist linked from [`specs/README.md`](../specs/README.md) and [`specs/alignment.md`](specs/alignment.md).
- **Architecture decisions**: engine, framework, library, storage, integration, and game-architecture choices are ADRs in [`specs/adr/`](../specs/adr/adr.md). The engine itself is chosen in [`specs/definition/definition.md`](../specs/definition/definition.md); its Engine ADR realizes that choice. Only Accepted ADRs authorize code. Do not read `specs/adr/archive/` unless explicitly asked.
- **Playtesting**: AI-agent playtests against design and UX per [`specs/playtest/`](../specs/playtest/playtest.md); evidence under [`docs/playtest/evidence/`](../docs/playtest/evidence/). Required at acceptance only when deliverables change playable behavior.
- **Aesthetics and assets**: the game's style (medium, pillars, palette, form, motion, interface and sound style) lives in [`specs/aesthetics/`](../specs/aesthetics/aesthetics.md), downstream of definition, quality, design, and view. Asset kinds, tool roles, procedures, and the catalog live in [`specs/assets/`](../specs/assets/assets.md); generation tools are Integration ADRs. Agent generation is optional. Agents may optionally touch up assets (background removal, inpainting, upscaling, and so on) with the options in [`docs/asset-tools.md`](../docs/asset-tools.md), which need no ADR; tools that doc bans (Pixellab) are never used. Make or change assets with `manage-asset`; catalog ones a person made, generated, or bought with `register-asset`; review them with `review-asset`. Only a person may exempt an asset from review, one at a time, recorded in the catalog. Every asset has a permanent asset ID (UUID version 7 from `.github/scripts/new_asset_id.py`, never typed) and a unique, readable handle `<kind-spec>/<name>`, recorded in one JSON entry file per asset that CI checks (`asset_catalog.py`).
- **Technical design**: code and data shape (layers, modules, components, contracts, schemata, sequences) live in [`specs/technical/`](../specs/technical/technical.md), downstream of definition, design, view, UX, and Accepted ADRs.
- **Concise docs/specs**: every file under `docs/` and `specs/` stays under **500 words**; split and link if longer. CI enforces it for Markdown (`Spec lint` `word-limit` check). Details: [`docs/README.md`](../docs/README.md), [`specs/README.md`](../specs/README.md).
- **Gameplay demos**: build with `create-gameplay-demo` under `demos/<slug>/`. They are exempt from SOLID but still spec first and spec-traced, and main code never imports them. Every demo is also a proof of concept for the style and the asset pipeline: it expresses `specs/aesthetics/` and uses only cataloged assets, each reviewed or exempted by a person ([`docs/demo-style-assets.md`](../docs/demo-style-assets.md)). To reuse demo behavior, use `promote-gameplay-demo` ([`docs/demos.md`](../docs/demos.md)).
